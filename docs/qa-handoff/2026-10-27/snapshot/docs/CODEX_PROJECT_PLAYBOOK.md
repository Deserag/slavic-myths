> **Приоритет владельца от 21.10.2026:** [#93](https://github.com/Deserag/slavic-myths/issues/93) «Лихо» — исполнительское ТЗ утверждено, статус «Ожидание», HP и художественный дизайн неизменны; не начинать кодирование без прямого поручения. Сразу после завершения и приёмки Лиха следующим поручением будет [#142](https://github.com/Deserag/slavic-myths/issues/142) — полный **аудит всех GitHub Issues и Project №9**; сейчас у #142 статус планирования «Ожидание». Codex обязан выяснить реальную готовность, owner acceptance и неактуальные задачи с доказательствами. Только готовить матрицу исправлений, без автоматических закрытий, метки `owner-accepted` или массовой смены статусов до отдельного решения владельца. Это решение новее прежней очереди художественных пакетов.


**Важное:** текущая доска — https://github.com/users/Deserag/projects/9/views/1. Миграция статусов [описана отдельно](PROJECT_MIGRATION_RUNBOOK.md); добавление конфигурации в репозиторий само по себе не означает, что карточка реально перенесена в Project.

**Для любой новой сессии Codex:** сначала [AGENTS.md](../AGENTS.md) (обязательный quality gate), [PROJECT_WORKFLOW.md](PROJECT_WORKFLOW.md), [PROJECT_STATUS.md](PROJECT_STATUS.md), [ROADMAP.md](ROADMAP.md), [ARCHITECTURE.md](ARCHITECTURE.md), затем **конкретная Issue и ВСЕ её обязательные дочерние Issues**, затем рабочий source/main и git status. Эта инструкция не разрешает начинать никакую задачу сама по себе.

## Разделение ролей

**Владелец** выбирает задачу, утверждает scope и приоритет, смотрит реальный игровой результат, принимает либо отправляет на доработку.  
**ChatGPT** помогает обсудить идею, анализирует source/issues, готовит индивидуальные ТЗ, поддерживает связанность родителя и дочерних задач, предлагает очередь. Не отправляет незаданные работы в исполнение.  
**Codex** осуществляет работу по *явному поручению владельца*. Нельзя самостоятельно переходить к «следующей по номеру» Issue, менять направление на похожий баг, объединять чужие подсистемы или чинить соседние дефекты «заодно». Сообщения без изменений в source не являются реализацией.

## Условия входа в работу

Перед началом Codex обязан:
1. Проверить, что Issue находится в **Ожидание** либо **Доработка**, есть разрешение владельца; либо что владелец явно велел продолжить уже начатую «В работе».
2. Прочитать именно текущий текст Issue, все связанные обязательные дети и критерии приёмки; учесть новые решения владельца поверх устаревшего текста. Номер задачи — идентификатор, **не порядок исполнения**.
3. Определить фактический HEAD, git status, наличие чужих worktree/несохранённых изменений и одного writer main. Если есть конфликт с другой активной работой — не делать reset/force/перезапись.
4. Записать точный scope и out of scope; не переименовывать registry ID, не ломать старые миры, лут, NBT, крафт, свойства и игровые механики вне согласованного задания.
5. Если из Issue выяснилось, что важные предпосылки ошибочны и реализация требует смены решения — **Анализ**. Не выдумывать новые требования самостоятельно.

## Работа и статусы

- При начале исполнения: **В работе**.
- После полного кодового результата и технических gates: **Тестирование**, если осталось только проверить результат владельцу.
- Игровое замечание владельца: **Доработка**; Codex фиксирует каждый наблюдаемый FAIL, делает ограниченные изменения, возвращает на «Тестирование».
- Если владелец изменил основу концепции: **Анализ**.
- **Готово** и **Отменена** устанавливает только владелец; Codex не выставляет owner-accepted, не закрывает Issue и не приписывает runtime PASS без реального запуска.
- Если Codex не имеет доступа к изменению **GitHub Projects Status**, он **не утверждает**, что статус поменялся: в итоговом комментарии пишет **Рекомендуемый статус Project: ... / Требуется изменение владельцем**. Не подменять поле Status редактированием заголовка Issue или придуманных labels.
- Project Status «Тестирование» сам по себе **не закрывает GitHub Issue** и не означает релиз. Для нескольких дочерних задач каждая сдаётся отдельно, родительский итог — только после всех обязательных результатов.

## Техническая сдача

В отчёте Codex обязательны:
- Issue и дочерние номера; HEAD/commit/source baseline; список изменённых production путей и registry ID.
- Что именно сделано, что оставлено без изменений и почему. Не выдавать документ или SVG-макет за внедрённую модель/PNG.
- **REQUIREMENT | EVIDENCE | PASS / FAIL / BLOCKED / NOT_RUN** по каждому обязательному критерию.
- Java 21 clean build, resource/assets checks, production JAR; фактический путь, версия, SHA256 (или честно «не создан/не проверен»).
- Для графики — настоящие before/after из реальных ресурсов/рендера при одинаковом масштабе; для звуков — оригинальность, фактические OGG, events/callsite, слышимое различие; для механик — тестовые сценарии, эффекты, граничные состояния.
- Для PolyMC — указать **BUILT / INSTALLED / NOT_INSTALLED** строго отдельно, installed JAR path/SHA, backup и отсутствие дублей, если установку действительно выполняли по поручению.
- Для Minecraft, GameTest, сервера, MP и реального FPS — **число фактических запусков**; всё, что владелец ещё не проверил, остаётся NOT_RUN/OWNER_PENDING и переносится в сценарий игрового тестирования.
- Что владельцу **конкретно проверить в игре**, включая контраст, анимацию, 1P/3P, мир/сохранения, случаи отказа. Если остались обязательные исполнительские блокеры или отсутствие production asset — не отправлять в «Тестирование».
- Один содержательный итоговый handoff после пакета, без шумных отчётов каждые пять-десять минут. При переходе в другую сессию — короткая передача состояния, а не повторный гигантский аудит.

## Как оформлять новые задачи

**Черновая идея**: Project Draft issue; заголовок, мысль, причина отсрочки и возможные источники. Статус «Концепция» без полноценного Issue в репозитории.

**Постановка**: после обсуждения перевести в «Анализ», собрать факты по реальному main, затем создать реальную Issue: проблема и воспроизведение → registry IDs / source paths → ожидаемое поведение → что не менять → зависимости/подзадачи → план QA → критерии приёмки. При утверждении владельцем — «Ожидание».

**Большая задача**: родительская Issue с независимым от номеров обязательным чек-листом детей. В родителе — полная карта/порядок, в каждом дочернем Issue — свой scoped результат и приёмочные условия. Не включать исправление другой подсистемы «по пути».

## ИГРОВАЯ ПРИЁМКА 25.10.2026 — обязательный шаблон handoff после реализации

Этот раздел **дополняет и конкретизирует** уже существующие правила. Источник: игровой отзыв 24–25.10.2026 и #269. На этапе восстановления 2.0 работать в ветке `hell`, `main` не менять до прямого разрешения владельца. Добавление задач #270–#283 не запускает работу.

### 1. Acceptance contract ДО кодирования
В явной таблице описать для каждой функции: `требование игрока → реальный entity/item/structure/advancement ID → условия → способ достижения БЕЗ читов → наблюдаемое действие → ожидаемый результат → ограничение старых сохранений → шаги QA`. Не считать существование ID или сборку успешной игрой. Для неопределённого дизайна (ветви достижений, редкость Сивки-Бурки, награды, эффекты украшений) представить на согласование визуальную схему/таблицу вероятностей и не заменять её личным выбором разработчика.

### 2. Сценарии по типу контента
- **Достижения:** один mod root/tab, содержательные тематические ветви; отдельное достижение у каждого настоящего босса, но без ненужных зависимостей несвязанных побед; серверный credit реальной победы, legacy прогресс, RU/EN, видимость GUI и связь с Книгой сказаний; отдельно creative/survival, старый мир, MP. Макет перед изменением дерева согласовать с владельцем.
- **Мобы/боссы:** зарегистрированный ID, biome/spawn placement, день/ночь, естественная вероятность на нескольких seed, независимое появление при отсутствии локации, дистанция, агрессия, убийство/награды. `/summon` проверяет только регистрацию, а не natural spawn. Сивка-Бурка требует отдельной проверки накопления шанса и гарантии возможности первой встречи к игровым дням 30–40 (уточнённая спецификация #271).
- **Структуры:** естественное появление, реальная близость и достижимость игроком, поиск по книге без OP, создание/проверка чанков, запрет разрушения построек, повторный поиск, отмена, сохранение, время первого размещения и MSPT. Результат `/locate` не заменяет фактическую постройку.
- **Предметы/лут:** получить предмет штатно; проверить атрибуты/урон/эффект в бою, экипировку Curios, снятие, задержку/дублирование, крафт/стадию игры, всю таблицу наград структуры и anti-duplication. Носимые предметы без работающего эффекта не объявлять полезным редким лутом.
- **Книги/NPC/ритуалы:** пройти от первого знания/разговора до реальной цели, боя и награды, проверить отсутствие устаревших «появится позже», корректность доверия и синхронизации GUI. Убийство в survival и вход в creative — разные сценарии Яги.
- **Визуал и клиент:** сравнение реального client render/анимаций/GUI разных масштабов, Jade/Xaero/FallingTree по конфигу тестового PolyMC, night vision/fog, старые и новые чанки. Native рендер моделей не равен игровому кадру.
- **Производительность:** latency нового мира, первого и повторного поиска/строительства, сохранения/перезахода; профилировка MSPT/tick/p95/p99/память, отрицательные сценарии и отчёт baseline→after без придуманного ускорения.

### 3. Формат ОБЯЗАТЕЛЬНОГО итогового ответа пользователю
```markdown
## Что сделал
- GitHub Issue, ветка, source HEAD, изменённые файлы/ID, краткое поведение до/после.

## Что проверил автоматически
- Команды build/test, сколько было реальных запусков Minecraft/GameTest/клиента, конкретный результат.
- JAR собран? где? SHA? Установлен в PolyMC? какой профиль? (BUILT != INSTALLED).

## Что ТЕБЕ проверить в Minecraft
Сборка/мир: <точные значения или честно неизвестно>
1. <точные действия в survival БЕЗ читов> → ожидаемый результат.
2. <проверка повторного действия / сохранения / отрицательного сценария> → ожидаемый результат.
3. <OP/команда только для диагностики, если нужна> → ожидаемый результат.
4. <отдельный мультиплеер/новый старый мир, где применимо> → ожидаемый результат.

## Осталось / риски
- FAIL, BLOCKED, NOT_RUN, известные граничные случаи, причина, что делать дальше.

## Статус
- REQUIREMENT | EVIDENCE | PASS/FAIL/BLOCKED/NOT_RUN
- Реальная приёмка владельца: OWNER_PENDING, если её не было.
- Следующая задача (без автоматического старта).
```
Если в сценарии от игрока требуются дополнительные неподтверждённые параметры, **сначала получить их до кодирования** или явно написать ожидаемую проверку на согласование. Не выдумывать существующие команды/registry ID, не выдавать после рабочего кода только `clean build PASS`.


### Уточнение структуры достижений — решение владельца 25.10.2026
Один корень/вкладка Slavic Myths; **ровно пять тематических основных ветвей**: «Хозяйство и быт», «Путешествия и открытия», «Сражения и боссы», «Сказания и союзники», «Ремёсла и магия». **Мор и проклятия — подраздел «Сражений и боссов», не шестая самостоятельная ветка**; победы над заражёнными/Моровым Лихом не требуются для другого независимого боя и могут случиться до Яги. **Путешествия и открытия** включают посещения реальных структур и территорий, **первое посещение Ада (Nether — измерение)**, **нахождение Навьей рощи (Nether — биом)**; новые биомы добавлять только после их фактической реализации и регистрации. По каждому реальному боссу отдельное видимое достижение, но не отдельная вкладка или root. Миграция/совместимость всех существующих критериев и достижений обязательна. До gameplay-изменений полный макет и реестр новых/старых ID передать владельцу на утверждение. Точное ТЗ: [#270](https://github.com/Deserag/slavic-myths/issues/270).
