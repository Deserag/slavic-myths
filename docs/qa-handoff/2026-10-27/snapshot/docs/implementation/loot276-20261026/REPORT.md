## Метод и ограничения

`tools/audit_loot276.py`: exact probability/expectation каждого предмета, weight selection, pool-level random_chance, rolls/count uniform, empty и nested loot_table. Luck=0, без Looting/влияния игрока. Set_damage/enchant меняют качество, не количество; зачарования не оцениваются в выдуманной валюте. Unsupported tables0. Формула отсутствия предмета: для одного pool `(1-c)+c*E[(1-p)^rolls]`; независимые pools/контейнеры перемножаются. Нет подмены весов шансами: weight не равен проценту.

**20 000 полных наборов контейнеров на каждый из6site/tier =120 000samples**; seed27600–27602для лагерей и27610–27612для курганов. Дополнительно **20 000actual pure Java KurganPlan/Layout на tier**, seeds0..19999, всего60 000планов: не копия алгоритма в Python. Гистограммы в native-plan-histogram.tsv; RNG loot-симуляции Python, не Minecraft, идентичность конкретных игровых seed не заявляется. Аналитические итоги усредняются по sampled manifest-frequency; округления до сотых. Файлы camp_*.json/kurgan_*.json содержат manifest, exact conditional/observed values и min/mean/max контейнеров. tables-exact.json хранит и27legacy tables.

**Это сумма контейнерных наград, НЕ весь фактический трофей зачистки.** Entity/equipment drops, сценарные личные выдачи, стойки/лошади/квестовые награды вынесены отдельно; численно складывать их в произвольную гарантированную полную награду нельзя без реального roster/условий убийства/права на personal reward. Время зачистки, риск по реальному бою, достижимость тайников, естественная частота, anti-dupe/MP/relog — NOT_RUN. Указанный ниже риск — относительная оценка по source, не измеренные минуты/MSPT.

## Конкретные варианты на утверждение — ничего не внедрено

**L1 — консервативный, предпочтительный.** Добавить ограниченный ценный roll только в одну обозначенную главную/казначейскую награду сооружения; текущий бытовой лут сохранить. Цели **на всё прохождение**, не на каждый из9–17сундуков:

| Site | P rune из ограниченногоI/IIпула | P perunite,quantity1–2 | Важное ограничение |
|---|---:|---:|---|
| Малый лагерь |5% tierI|0%|Никакой гарантии сильного предмета |
| Средний лагерь |20% tierI,не story|8%|Количество coin не повышать |
| Большой лагерь |35% any доступнойI/II,с учётом нынешних25.16%|25%|Это целевой общий шанс, НЕ плюс35% поверх существующихrolls |
| КурганI,V2 |8% tierI|0%|Не превращать3контейнера в богатый рейд |
| КурганII,V2 |25% I/II|12%|Главная/казначейская награда; прочие находки остаются коллекционными |
| КурганIII,V2 |45% I/II|30%|Boss soul/персональные награды сохранены отдельно; не random IV/уникальный призыв |

Чтобы это не дало45% в каждом из17контейнеров, до внедрения нужно закрепить конкретную единственную точку дорогого roll на план/структуру. Это часть следующего отдельного дизайна #276, здесь новый marker/state/table assignment не создавался. Для большого лагеря сохранить тематические forge/warehouse/Соловей награды и пересчитать перекрытие текущих rune pools.

**L2 — распределённый вариант.** Без нового единственного prize-контейнера: использовать только существующие тематические таблицы. Для desired whole-site P и nравнозначных контейнеров `q=1-(1-P)^(1/n)`. Пример medium:20%anyrune при9контейнерах требует q≈2.449%на контейнер, а не20%;8%perunite →q≈0.922%. Для nпеременного новый q даёт диапазон, поэтому калибровать на actual native-plan histogram, не гарантировать точное Pвсех seed. При этом не размножать шанс на7типовруны по20%. Вариант проще по существующим таблицам, но хуже контролирует целое сооружение и требует второй20k+симуляции **после утверждения**. Выбор L1/L2,точные ID/числа и допустимые аксессуары — решение владельца.
