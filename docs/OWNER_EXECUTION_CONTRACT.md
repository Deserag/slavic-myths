# Обязательные правила владельца: постановка и исполнение задач ChatGPT / Codex
**Решение владельца от 01.11.2026.** Обязательно перед **каждой** новой задачей, исправлением, исследованием состояния и промптом исполнителю. Приоритет над устаревшими инструкциями, противоречащими этому решению. Дополняет `AGENTS.md`, `docs/BRANCH_POLICY.md`, `docs/PROJECT_WORKFLOW.md`, `docs/CODEX_PROJECT_PLAYBOOK.md` и `docs/requirements/`. Работы не запускаются без прямого поручения владельца.

## 1. Одна реализация — одна полноценная GitHub Issue
- Прежде чем писать код, создавать модель, патч, структуру, UI, звук либо исправлять баг, **найти актуальную Issue**. Если её нет — **создать Issue до реализации**. Никакой разработки «просто в ветке», «в чате» или «по памяти».
- Отдельная реализуемая функция / независимый босс / самостоятельное исправление — отдельная Issue. Для взаимозависимого пакета — родительская Issue и дочерние Issues с чёткими границами. Объединение возможно только если владелец явно утвердил единый неделимый scope.
- Проверять **Issues + PR + все релевантные ветки + фактический код и ресурсы**, а не один поиск по заголовкам. Существование ветки/PR не доказывает ни отсутствие задачи, ни готовность. Если работа уже сделана, сначала сравнить её с актуальной Issue — не начинать заново вслепую.
- У каждой Issue: точное название, версия, ссылка на ветку, файлы/registry IDs, полный объём, исключения, зависимости, критерии приёмки, статус и доказательства.

## 2. Реальный художественный референс или чертёж ОБЯЗАТЕЛЕН внутри задачи
- Для любой визуальной реализации **приложить или дать прямую работающую ссылку** на утверждённый владельцем оригинал: PNG (листы спереди/сбоку/сзади/¾ и крупные детали), чертёж, editable Blockbench/UV и необходимые дополнительные эталоны. В Issue фиксировать **конкретный путь/URL, имя файла, версию и при наличии SHA-256**, какой файл принят владельцем и его приоритет.
- **Проверить фактическую доступность каждого референса для исполнителя до промпта и до кодирования**. Написать только имя `...APPROVED.png`, сослаться на отсутствующий ZIP, беседу или Library без доступного файла — **НЕ значит предоставить референс**. Техническая SVG-схема или текст НЕ подменяют художественный оригинал, если он утверждён как главный эталон.
- Если исходник недоступен: `BLOCKED_ART_SOURCE`; явно указать недостающий файл и не заявлять визуальное соответствие или сдачу. Не дорисовывать/не придумывать собственный «похожий» вариант вместо согласованного.
- Задача ChatGPT/Codex — **максимально точно воспроизвести утверждённый образ в реальной игре**, а не сделать поверхностно похожий концепт. Совпадать должны геометрия, силуэт, пропорции, цвета, материалы, текстура, выражение, позы, анимации, VFX и масштаб. В финале нужны кадры **из Minecraft** с теми же ракурсами рядом с референсом. Эталон на картинке ≠ работающая модель.

## 3. Детальное техническое задание на КАЖДУЮ составляющую
- В Issue перечислить каждую видимую и функциональную деталь, без фраз «сделать красиво/похоже»: форма частей, число сегментов/конечностей, размеры в блоках, соотношения со Steve, палитра, текстуры/UV/emissive, отдельные bones/pivots, перед/бок/спина/¾, анимации и переходы, контакты и серверные hit windows, звуки, частицы, фазы, атаки, AI, спавн, сохранения, MP, производительность и ограничения мира — **только применимое к конкретной работе**.
- Для каждой детали: **требование → точный фрагмент референса/источника → путь реализации/существующий код → наблюдаемый ожидаемый результат → проверка/доказательство**. Не оставлять обязательные мелочи за пределами ТЗ, не изобретать неодобренные параметры. Незаданные числа/неутверждённые изображения честно обозначать как требующие решения владельца, а не объявлять утверждёнными.
- Визуальная часть — самостоятельный обязательный gate: **геометрия + пиксельная текстура + UV + цвет/материал + анимации + эффекты + игровой размер**. Исправить только геометрию и оставить неверную внешность — **НЕ ИСПРАВЛЕНО**.

## 4. Строжайший scope: не трогать лишнее
- Делать **только то, что владелец поручил и что входит в указанную Issue**. В промпте отдельно написать `IN SCOPE` и `OUT OF SCOPE`.
- Запрещены самовольная работа над соседними боссами, механиками, предметами, наградами, балансом, квестами, рецептами, биомами, инфраструктурой, перестройкой архитектуры, «улучшениями заодно» и ненужной отчётностью. Критическую зависимость выявить и согласовать как отдельную работу; не раздувать scope.
- Не делать destructive git-операций, не перетирать чужой worktree/коммиты, не менять `main` без прямого разрешения.

## 5. Перед КАЖДЫМ промптом точно указать место исполнения
- Первые строки **каждого** промпта исполнителю: `Repository: Deserag/slavic-myths`; `Issue: #...`; `Base/integration branch: ...`; `Working branch: ...`; `PR target: ...`; конкретные source/resource/reference paths и `HEAD`, когда он известен. Перепроверять **актуальную** `docs/BRANCH_POLICY.md` и git status/HEAD: исторические ветки `hell`, `2.2`, `2.3` не назначать автоматически.
- На 01.11.2026 для пары сестёр действующая интеграционная ветка — **`3.3`**, реализация — `feat/3.3-paired-sisters-bosses-20261101` (проверять свежий HEAD; исходная feature-ветка может уже быть интегрирована). `main` не трогать. Для других задач цель определять по свежей политике, а не по названию старого Issue.
- После путей перечислить утверждённые референсы, что разрешено и запрещено менять, минимальный план проверки и **измеримый результат**, а не просьбу «что-нибудь улучшить».

## 6. Быстрая, настоящая реализация вместо имитации прогресса
- Приоритет — полноценный работающий и визуально соответствующий результат **в пределах указанного scope**, затем краткая проверка. Не подменять проблему отдельной правкой геометрии, документом, SVG, регистрацией entity, компиляцией или количеством тестов.
- `clean build PASS` не равен `Minecraft runtime PASS` и не равен `ART_PASS`. До реальных кадров, нужных игровых/серверных проверок и приёмки владельца статус `IN_PROGRESS` / `NOT_RUN` / `BLOCKED`, а не `DONE`. Только владелец закрывает Issue и принимает визуал.
- Если тестовую игру нельзя запустить безопасно без воздействия на рабочий стол владельца, ставить `BLOCKED_ISOLATION`, не подменять снимками из редактора или утверждением «всё проверено».

## 7. Жёсткая экономия времени, чата и токенов
- Ответы владельцу **максимально краткие, предметные и быстрые**: что найдено/сделано, что реально не сделано, где ветка/Issue/PR, что мешает, ближайшее конкретное действие. Без огромных отчётов, повторных пересказов, многократных извинений, лишней телеметрии и промежуточного шума.
- Не перечитывать всё подряд и не гонять одинаковые поиски: сначала точные Issue, ветка, diff и нужные файлы; использовать существующие документы/матрицы и адресно проверять только требования текущей работы. Длинный чат, число токенов, объём отчёта и длительность обсуждения **не считаются результатом**.
- При переходе в новую беседу — короткий checkpoint со ссылками на Issue/ветку/источники и честным остатком работ. Не переносить гигантские журналы и не повторять уже проведённое исследование без причины.

## Обязательный короткий контроль до выполнения
`ISSUE EXISTS → EXACT BRANCH/HEAD → APPROVED ORIGINALS OPENABLE → PER-DETAIL REQUIREMENTS → IN/OUT SCOPE → REAL SOURCE WORK → IN-GAME ART & GAMEPLAY QA → OWNER ACCEPTANCE`.

Любое отсутствие обязательного шага означает явный `BLOCKED` / `NOT_RUN`; **не выдумывать успех**. Для работы, не требующей визуала, референс означает проверяемую спецификацию/макет/ожидаемый результат, а не обязательное изображение там, где оно не нужно.
