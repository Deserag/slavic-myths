1. Открыть **уже созданный [Project №9](https://github.com/users/Deserag/projects/9/views/1)** и проверить его название, тип вида и возможность редактирования. Повторный Project не создавать.

3. На странице https://github.com/Deserag/slavic-myths/projects выбрать **Link a project**, если доска ещё не появилась автоматически. Выбрать проект того же владельца.
4. В **Project settings → README** поместить краткое описание ниже и ссылки на этот файл, [рабочий процесс](PROJECT_WORKFLOW.md), [Codex](CODEX_PROJECT_PLAYBOOK.md) и [AGENTS.md](../AGENTS.md).
5. Создать поля, представления и workflow, описанные ниже. Сначала вручную импортировать уже существующие Issues; встроенный **Auto-add не добавляет задним числом** существовавшие раньше задачи.

## Поля

| Поле | Тип | Варианты / смысл |
|---|---|---|
| Status | **Single select**, основной | **Концепция, Анализ, Ожидание, В работе, Тестирование, Доработка, Готово, Отменена** |
| Priority | Single select | P0 — критично; P1 — важно; P2 — полировка |
| Релиз | Single select | 2.0; 2.1; 3.0; Будущее / не определено |
| Направление | Single select | Существа; Оружие; Броня и одежда; Руны; Арт предметов; Мир и генерация; Механики; Интерфейс; Аудио; Производительность и QA |
| Порядок | Number | Приоритет **внутри очереди**. Меньше число — раньше. Только владелец/планирование меняет порядок. |

Не добавлять дублирующие Label «status:done» и подобные. Для блокировки достаточно зависимости Issue и отчёта BLOCKED; отдельный признак «Отложено» можно сделать меткой только при реальной необходимости. GitHub Issue labels P0/P1/P2 из существующих заголовков не заменяют поле Priority.

## Автоматизация

- **Auto-add to project** для **Deserag/slavic-myths**, фильтр **is:issue**. Автоматически подтягивать новые реальные Issues, а не PR как отдельные задания. Project Draft issues для ранних идей создаются прямо в «Концепции».
- **Item added → Анализ** только для новых обычных Issues (если Project workflow это поддерживает). Уже согласованные задачи можно вручную перевести в «Ожидание».
- **НЕ включать** безусловное **Issue closed → Status: Готово**: закрытое not_planned/duplicate не является принятой реализацией. «Готово» и «Отменена» различаются по решению владельца.
- **НЕ включать** workflow, который переводит Issue в «Готово» при PR merge/commit/build. Это нарушит AGENTS.md.
- Сохранить существующий owner acceptance guard: владелец подтверждает completed, а осознанно отменённая задача закрывается как not_planned/duplicate. Если GitHub Actions ошибочно переоткрывает явно отменённую Issue, исправлять правило **точечно по подтверждённому владельцем случаю**, а не отключать защиту целиком.

| #81, #96–101 — материалы | Частичная реализация; по каждой дочерней Issue выбрать «В работе» / «Ожидание» / «Тестирование» отдельно |

Исторические закрытые Issue автоматически в «Готово» не переносить. Подзадачи, закрытые после выпуска лишь спецификации, и отдельные ранее внедрённые изменения в одной Issue сначала сверять с отчётами. Для **родительских задач** статус должен отражать полный состав дочерних пунктов.

## Первичная техническая проверка проекта

После настройки ответственный проверяет: URL проекта действителен; он виден во вкладке Projects репозитория; Default repository верен; все восемь статусов работают; новая Issue подтягивается в доску; тестовая Draft issue остаётся концепцией; закрытие not_planned не помечается «Готово»; #92 стоит выше #87; #105 не доступна как немедленное поручение до #104; ранее реализованные пакеты не стартуют заново только из-за старых статусов.
