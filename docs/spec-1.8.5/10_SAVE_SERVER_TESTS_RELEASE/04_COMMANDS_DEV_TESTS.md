# Отладка, команды и контролируемые тесты

## Сначала использовать штатный test/dev interface
Если у мода уже есть debug commands или `/slavicmyths ...`, добавить подкоманды к нему, не регистрировать второй корневой command namespace. Все команды только оператору уровня 2+ / существующим dev-правам.

## Только для проверки
- `quest185 status <player>` — вывести главу, trust gates, 6 стадий и W1–W3, invitation, persistent state.
- `quest185 reset <player>` — сбросить **только** сюжет 1.8.5, не старый trust, руны, предметы, мирового босса; не удалять существующую книгу.
- `quest185 invite <player>` — отправить тестовое приглашение/проверить нужного отправителя.
- `quest185 stage <player> <id> <state>` — установить только stage, test server only / operator.
- `quest185 debug_actors <player>` — показать условия участия Яги/Баюна/Волка в ближайшей сцене без правки trust.
- `quest185 wolf_call <player>` — вызвать тест-помощника по тем же правилам cooldown/owner, либо явно операторский bypass без релизного доступа.
- `quest185 cleansing_sample <player>` — выдать порошок для тестирования без обхода проверки серверного права.

## Названия команд
Приведены как функциональная форма, а не обязательно готовый синтаксис; адаптировать к реально зарегистрированному командному корню проекта и отобразить окончательный синтаксис в итоговом отчёте. Если debug-командный блок у мода отсутствует — сделать минимальный операторский подкласс со строго этими действиями, без целой новой чит-системы.

## Что НЕ делать
Не добавлять dev-команды в обычные survival craft recipes. Не писать `slavicmyths:mor_wolf` как «готовую команду», если регистр не существует. Не открывать пользователю операторские служебные экраны при обычном прохождении.
