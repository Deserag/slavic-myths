# СТРОГИЕ ограничения для Codex — прочитать до анализа репозитория

1. **Только версия 1.9.1.** Не трогать Карачуна/Змеиную гору/Полоза/новые измерения, не менять roadmap самовольно, не расширять список существ.
2. **Экономия токенов:** запрет на полный аудит/индексацию репозитория. Сначала локально посмотреть список целевых директорий и **точечно** открыть существующую регистрацию сущностей, модели/рендереры, анимации, звуки, предметы, руны, UI способностей, существующие квесты Бабы-яги/Баюна, сохранение/сетевые пакеты, сборку. Затем работать только с файлами, которые нужны 1.9.1.
3. **НЕ запускать Minecraft, PolyMC, `runClient`, `runServer`/UI walkthrough** ни прямо, ни скрыто, без явного разрешения пользователя. Визуальное игровое QA выполнит пользователь. Можно выполнить компиляцию и нетребующие запуска Minecraft проверки средствами проекта; если Gradle-задача запускает игру, НЕ вызывать её.
4. Не запускать массовые автоформатирования, upgrade Minecraft/Forge/mappings/Java, не переписывать архитектуру, не обновлять десятки unrelated файлов. Никаких незапрошенных refactor.
5. Текущую версию Minecraft/Forge/Java/Gradle **считать непосредственно из конфигурации текущей ветки `main`**; не копировать слепо номера из старых дорожных карт. Использовать только реальные доступные API и методы данной версии. Не выдумывать библиотек, классов, ресурсов, классовых имен.
6. **Внешний вид: Minecraft voxel**, не реальная иллюстрация. У Морозко и всего лута отличимые самостоятельные модели/текстуры: никакого плоского синего `recolor` обычного моба, предмета-палки без навершия, невидимого двойника или стандартной текстуры снежка вместо посоха.
7. **Ресурсы в папке `02_REFERENCES` — реальные референсы**, не пытаться подставить картинку из ТЗ как готовую Minecraft-текстуру целиком. Из неё поэлементно воссоздать художественное исполнение средствами модели/UV/PNG/частиц.
8. Любой новый UI/текст/название/тултип, а также сообщение о наградах, командах и статусе — **на русском**, дополнительно английские переводы по существующей схеме локализации. Убедиться, что `ru_ru` не показывает сырые registry keys.
9. Никаких пустых обещаний: не писать «готово», если нет реальных классов, ресурсов и работающих переходов состояния. Если лимит ограничен — завершить внутренне целостный блок и честно зафиксировать невыполненное; не имитировать готовность всего патча.
10. Новые рецепты, награды и доступ должны образовывать **реальную достижимую цепочку**. Проверить, что предмет вызова реально получается у существующих NPC; рунный предмет вставляется в актуальную систему; посох можно применить; амулет действует в слоте аксессуаров.
11. Не переносить выполненную работу в `master` или release-ветку, не выпускать ZIP-модpack/PolyMC instance по собственной инициативе. Работать в текущей ветке, обычно `main`, только после проверки.
12. Не создавать геймплей, который требует у игрока дополнительных модов, если этого не требует текущий проект; повторное использование интеграций — только при наличии.
13. Не ссылаться на несуществующие магические эффекты «должно работать». Все эффекты либо через зарегистрированные эффекты, либо серверную логику с корректным sync/UI.
14. **Последние патчи ветки 1.9** зарезервированы на общую ревизию слабой прокачки (например, rune III); именно в 1.9.1 эту систему глобально НЕ переделывать, только точечно интегрировать две наградные руны.
15. Любой случайный результат рассчитывается **на сервере и на каждого награждаемого игрока отдельно**, а не клиентом и не одной кучей лута на земле.

## Порядок при невозможности уложиться в доступный ресурс
Сначала обеспечить complete entity + trial + 5%-completion + визуальные assets + гарантированные награды. Затем уникальные боевые способности, потом посох/копия игрока/руны и полировка. Ни один пункт нельзя объявлять реализованным, пока механика и ресурс не подключены. Если работу придётся разбить по итерациям, оставь точный `04_QA/02_IMPLEMENTATION_STATUS_TEMPLATE.md` с actual vs planned, не запускай игру.
