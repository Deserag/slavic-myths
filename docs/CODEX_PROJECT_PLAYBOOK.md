Сразу после завершения и приёмки Лиха следующим поручением будет [#142](https://github.com/Deserag/slavic-myths/issues/142) — полный **аудит всех GitHub Issues и Project №9**; сейчас у #142 статус планирования «Ожидание». Только готовить матрицу исправлений, без автоматических закрытий, метки `owner-accepted` или массовой смены статусов до отдельного решения владельца. Это решение новее прежней очереди художественных пакетов.


**Важное:** текущая доска — https://github.com/users/Deserag/projects/9/views/1. Миграция статусов [описана отдельно](PROJECT_MIGRATION_RUNBOOK.md); добавление конфигурации в репозиторий само по себе не означает, что карточка реально перенесена в Project.

**Для любой новой сессии Codex:** сначала [AGENTS.md](../AGENTS.md) (обязательный quality gate), [PROJECT_WORKFLOW.md](PROJECT_WORKFLOW.md), [PROJECT_STATUS.md](PROJECT_STATUS.md), [ROADMAP.md](ROADMAP.md), [ARCHITECTURE.md](ARCHITECTURE.md), затем **конкретная Issue и ВСЕ её обязательные дочерние Issues**, затем рабочий source/main и git status. Эта инструкция не разрешает начинать никакую задачу сама по себе.

## Разделение ролей

**Владелец** выбирает задачу, утверждает scope и приоритет, смотрит реальный игровой результат, принимает либо отправляет на доработку.  
**ChatGPT** помогает обсудить идею, анализирует source/issues, готовит индивидуальные ТЗ, поддерживает связанность родителя и дочерних задач, предлагает очередь. Не отправляет незаданные работы в исполнение.  
**Codex** осуществляет работу по *явному поручению владельца*. Нельзя самостоятельно переходить к «следующей по номеру» Issue, менять направление на похожий баг, объединять чужие подсистемы или чинить соседние дефекты «заодно». Сообщения без изменений в source не являются реализацией.

## Условия входа в работу

Перед началом Codex обязан:
1. Проверить, что Issue находится в **Ожидание** либо **Доработка**, есть разрешение владельца; либо что владелец явно велел продолжить уже начатую «В работе».
2. Прочитать именно текущий текст Issue, все связанные обязательные дети и критерии приёмки; учесть новые решения владельца поверх устаревшего текста. Номер задачи — идентификатор, **не порядок исполнения**.
3. Определить фактический HEAD, git status, наличие чужих worktree/несохранённых изменений и одного writer main. Если есть конфликт с другой активной работой — не делать reset/force/перезапись.
4. Записать точный scope и out of scope; не переименовывать registry ID, не ломать старые миры, лут, NBT, крафт, свойства и игровые механики вне согласованного задания.
5. Если из Issue выяснилось, что важные предпосылки ошибочны и реализация требует смены решения — **Анализ**. Не выдумывать новые требования самостоятельно.

## Работа и статусы

- При начале исполнения: **В работе**.
- После полного кодового результата и технических gates: **Тестирование**, если осталось только проверить результат владельцу.
- Игровое замечание владельца: **Доработка**; Codex фиксирует каждый наблюдаемый FAIL, делает ограниченные изменения, возвращает на «Тестирование».
- Если владелец изменил основу концепции: **Анализ**.
- **Готово** и **Отменена** устанавливает только владелец; Codex не выставляет owner-accepted, не закрывает Issue и не приписывает runtime PASS без реального запуска.
- Если Codex не имеет доступа к изменению **GitHub Projects Status**, он **не утверждает**, что статус поменялся: в итоговом комментарии пишет **Рекомендуемый статус Project: ... / Требуется изменение владельцем**. Не подменять поле Status редактированием заголовка Issue или придуманных labels.
- Project Status «Тестирование» сам по себе **не закрывает GitHub Issue** и не означает релиз. Для нескольких дочерних задач каждая сдаётся отдельно, родительский итог — только после всех обязательных результатов.

## Техническая сдача

В отчёте Codex обязательны:
- Issue и дочерние номера; HEAD/commit/source baseline; список изменённых production путей и registry ID.
- Что именно сделано, что оставлено без изменений и почему. Не выдавать документ или SVG-макет за внедрённую модель/PNG.
- **REQUIREMENT | EVIDENCE | PASS / FAIL / BLOCKED / NOT_RUN** по каждому обязательному критерию.
- Java 21 clean build, resource/assets checks, production JAR; фактический путь, версия, SHA256 (или честно «не создан/не проверен»).
- Для графики — настоящие before/after из реальных ресурсов/рендера при одинаковом масштабе; для звуков — оригинальность, фактические OGG, events/callsite, слышимое различие; для механик — тестовые сценарии, эффекты, граничные состояния.
- Для PolyMC — указать **BUILT / INSTALLED / NOT_INSTALLED** строго отдельно, installed JAR path/SHA, backup и отсутствие дублей, если установку действительно выполняли по поручению.
- Для Minecraft, GameTest, сервера, MP и реального FPS — **число фактических запусков**; всё, что владелец ещё не проверил, остаётся NOT_RUN/OWNER_PENDING и переносится в сценарий игрового тестирования.
- Что владельцу **конкретно проверить в игре**, включая контраст, анимацию, 1P/3P, мир/сохранения, случаи отказа. Если остались обязательные исполнительские блокеры или отсутствие production asset — не отправлять в «Тестирование».
- Один содержательный итоговый handoff после пакета, без шумных отчётов каждые пять-десять минут. При переходе в другую сессию — короткая передача состояния, а не повторный гигантский аудит.

## Как оформлять новые задачи

**Черновая идея**: Project Draft issue; заголовок, мысль, причина отсрочки и возможные источники. Статус «Концепция» без полноценного Issue в репозитории.

**Постановка**: после обсуждения перевести в «Анализ», собрать факты по реальному main, затем создать реальную Issue: проблема и воспроизведение → registry IDs / source paths → ожидаемое поведение → что не менять → зависимости/подзадачи → план QA → критерии приёмки. При утверждении владельцем — «Ожидание».

**Большая задача**: родительская Issue с независимым от номеров обязательным чек-листом детей. В родителе — полная карта/порядок, в каждом дочернем Issue — свой scoped результат и приёмочные условия. Не включать исправление другой подсистемы «по пути».

## Пример краткого handoff между ChatGPT и Codex

**Владелец поручил:** Issue #NNN.  
**Project Status:** Ожидание → В работе.  
**Scope:** строго пункты из указанной Issue и обязательных детей.  
**Начать:** AGENTS.md → PROJECT_WORKFLOW.md → CODEX_PROJECT_PLAYBOOK.md → project docs → Issue и source/main.  
**Выход:** реальные изменённые файлы, матрица доказательств, build/JAR, сценарии владельца, рекомендуемый статус «Тестирование» при соблюдении gate.  
**Нельзя:** исправлять незаказанные задачи, ставить «Готово», owner-accepted или автоматически закрывать GitHub Issue.
