# 03 — Файлы, ресурсы, рецепты, интеграция

Документ описывает **области ответственности**, не список файлов, которые нужно обязательно менять. Пользоваться текущей структурой проекта, а не создавать одноимённые дубликаты классов.

## 1. Приоритетный код (разрешённые точки изменения)

| Область | Рекомендуемые текущие файлы / ответственность |
|---|---|
| ID, совместимость, чтение/запись/наковальня | `src/main/java/org/slavicmyths/rpg/Runes.java`, `RuneRework.java`, `RuneDefinition.java`, `RuneBalance.java` |
| Старые боевые эффекты | `rpg/RuneEffects.java`, `rpg/RpgEvents.java`, `rpg/RuneRuntime.java` |
| Казнь боссов/перки | `rpg/RareRuneRuntime.java`, `rpg/RareRuneRules.java` при необходимости |
| Морозко | `morozko/FrostCold.java`, `FrostEvents.java` + фактические подписчики применимости эффекта после проверки |
| Подавление | `rewards/RewardEvents.java`, при необходимости `RewardRunes.java` |
| Кирка/скорость добычи | `industry/MiningRunes.java` и актуальный обработчик скорости разрушения |
| Способ получения IV | `yaga/YagaServices.java` и **минимальный** существующий gate у интерфейса обмена; чтение подтверждённого прогресса Горыныча без изменения логики награды |
| UI существующей наковальни / JEI | `client/RuneAnvilScreen.java`, `compat/JeiRunes.java` — менять **только если необходимо** и не дублировать действующее отображение |
| Сохранение/tooltip | `item/ItemState.java`, `rpg/RuneRepair.java` — менять **только после доказательства необходимости**; миграцию данных не добавлять «на всякий случай» |
| Новая функциональность | Разрешены небольшие `rpg/*Rune*`/`rpg/*III*` классы, если это уменьшает риск изменения многопоточного боевого монолита. Один источник истины на эффект, не две дублирующие подписки |

**Охраняемые смежные зоны:** `combat/*`, `item/*` с боевой базой, `gorynych/Gorynych*.java`, `poloz/*.java`, `morozko/Morozko.java`, `karachun/*`, уникальная броня/оружие, `client/*Renderer` и оружейные `models`. Только узкое чтение, корректировки без переписывания текущей работы параллельных патчей. При необходимости изменений за пределами этих точек — указать файл, причину, риск и минимальный дифф.

## 2. ID и обязательные ассеты

Для каждого нового ID из `01_IMPLEMENTATION.md`:

- Зарегистрированный предмет `slavicmyths:rune_<id>` в **существующем реестре**, со ссылкой в `Runes.IDS`, `RuneDefinition.ALL`, матрице совместимости, creative tab и tooltip. `rune_veles_oath_iv` — `Rarity.EPIC`, четыре III — `Rarity.RARE` или соответствующий принятой стилистике rarity. Не создавать третий способ регистрации помимо текущих `ModItems` / `RuneRework`.
- `src/main/resources/assets/slavicmyths/models/item/rune_<id>.json` — модель с `layer0` на собственную текстуру.
- `src/main/resources/assets/slavicmyths/textures/item/rune_<id>.png` — пять уникальных PNG по `02_VISUAL.md`.
- Переводы в `assets/slavicmyths/lang/ru_ru.json` и `en_us.json`:
  - `item.slavicmyths.rune_<id>`: «Руна Ответного удара III», «Руна Охотника III», «Руна Последнего рубежа III», «Руна Глубин III», «Руна Велесовой клятвы IV» и корректные английские названия.
  - локализованный текст фактических процентов/секунд, условий, типа совместимого предмета, таймера, источника получения, стадии доступа и состояний «ожидание», «неактивно/несовместимо»; не хранить числа независимо от правил.
- Не менять `textures/item/rune_*.png` для существующих ID. Не изменять другие `models/item/*.json`.

## 3. Рецепты (4 файла)

Создать 4 JSON-файла в `src/main/resources/data/slavicmyths/recipe/` по актуальному образцу `rune_rework_blood.json` / `rune_foundation_blank_3.json`:

1. `rune_rework_counterstrike_iii.json`
2. `rune_rework_hunter_iii.json`
3. `rune_rework_last_stand_iii.json`
4. `rune_rework_depths_iii.json`

Каждый: `"type":"slavicmyths:rune_crafting"`, первая input-группа `slavicmyths:blank_rune_3` 1 с `base:{"tier":3,"material":"perunite"}`, ещё две группы с числами из ТЗ, `result.id` — собственный зарегистрированный предмет, `result.count=1`; по текущему крафтовому аналогу `chisel:false`. Не добавлять рецепт создания IV и не изменять стоимость получения `blank_rune_3`. Убедиться, что **одна и та же комбинация ингредиентов не конфликтует** с существующим рецептом; JEI обязан показать четыре результата ровно по одному разу.

## 4. Теги

- `src/main/resources/data/slavicmyths/tags/entity_type/rune_death_immune.json`: дополнить после фактической сверки реестра поздних боссов и особых квестовых сущностей. Тег должен проходить data load; **никогда не угадывать ID**.
- Если необходим свой Slavic Myths tag руд, создать его в `data/slavicmyths/tags/block/` и включать только реально зарегистрированные блоки; стандарт `#c:ores` поддерживать через существующие NeoForge/common tags. Не менять текстуры самих руд или таблицы дропа.
- `data/slavicmyths/tags/item/rune_melee_weapons.json`, `rune_staff.json` и теги вместимости относятся к пересечению с патчем оружия: сначала прочитать актуальное состояние, **не** перезаписывать списки целиком и не удалять введённые тем патчем категории.

## 5. Нетронутые источники получения

Сохранить без балансных правок лут `nightingale`, `likho_one_eyed`, `tugarin_zmey`, `kurgan_voevoda`, шахтёрские источники/торговлю, выдачи богатырей, морозный суд, испытание Карачуна, Полоза, Горыныча, существующие обмены Бабы-яги. Новая строка обмена Велесовой клятвы добавляется **сверх** имеющихся, не вместо награды/чешуи/трёх рун Горыныча. Нельзя выдавать новую IV при креативном/standalone фарме босса без сюжетного зачёта.

## 6. Контроль границ diff

Перед итоговой сборкой вывести `git diff --stat`, затем выборочно проверить дифф общих файлов и наличие актуальных чужих изменений. Не использовать `git checkout -- .`, не перегенерировать сотни JSON, не форматировать массово `ru_ru/en_us`, не перемещать файл без нужды, не переписывать игровые registries «на будущее». Не добавлять README/ROADMAP/CHANGELOG с придуманными номерами версии без запроса автора.
