## 3. Реализационные этапы и бинарная приёмка

### A. #289 — проектирование по утверждённым оригиналам

После SOURCE PASS: inventory уже зарегистрированных IDs, закрепление кандидатов из `docs/implementation/lost-halls-source-gate/id-plan.tsv` после проверки registry, палитра камня №3 (первый ряд, **третий**, не №1), floorplan и минимум три разреза естественной многоуровневой зоны. Составить схему S1–S6, входы/выходы, обходы лавы и границы чанков. `PASS` только с оригинальными SHA, визуальной картой и разрешённым владельцем baseline; иначе `BLOCKED_REFERENCE`.

### B. #290 — четыре семейства материалов

`lost_hall_stone`, `cracked_lost_hall_stone`, `luminous_vein_stone`, `cave_coating` (ID — кандидаты, до регистрации сверить). Для основного/полированного камня нужны ступени/плиты/стены и рецепты. Полноценные DeferredRegister, states, models, textures, item models, loot/mining, creative tab, RU/EN. Светожилы локальные, с нормальным vanilla block light, **не** новая руда; налёт тонкий, не закрывает путь. Никакой новой древесины. Все блоки визуально сравнить с оригиналом и с проверенными игровыми кадрами.

### C. #291 — шесть видов связной геометрии

S1 извилистые коридоры; S2 поддержанные мосты; S3 огромный каменный зал; S4 ванильные грибные оазисы; S5 локально светящиеся гроты; S6 развилки. **Натуральный многоярусный лабиринт**, не шахматка биомов и не одинаковая квадратная крепость. Разработать seed-based, bounded chunk-safe план/граф с уникальными room/arena IDs, детерминированным clipping на границах 2/4 чанков и доступными путями туда/назад. Финальный voxel snapshot должен проходить `LostHallsRouteCheck.verify` до `LostHallsRooms.registerCompleted`. Не публиковать ложные частично построенные комнаты; различать финализацию всех частей и повторную публикацию при смене порядка чанков. Нужны доказательства сцепления маршрутов, иначе `BLOCKED_DEPENDENCY`.

### D. #292 — пять самостоятельных живых мобов

**Ровно 5 EntityTypes:** Шептун (**60 HP**, один entity type, **4 устойчивых NBT-окраски** красная/зелёная/чёрная/фиолетовая, hostile ranged); Оскольник (**90**, hostile ranged); Гулокрыл (**30**, настоящий приручаемый летающий питомец, owner/heal/follow/fire bolt, state после reload); Эховик (**60**, нейтральный, возмездие только после провокации); Грибошмыг (**60**, мирный, взаимодействие кормлением). Все реальные ModelPart/UV/анимации, AI cooldown/LOS, серверный контроль, корректный natural spawn по S1–S6. Исключены «Стенолаз» и «Жильник». Не делать подмены vanilla мобами с новым названием.

### E. #301 — награды и средства ориентирования

Шептун: `lost_whisper_thread` **0–2**; Оскольник: `lightvein_shard` **1–3**; Эховик: `echo_vial` через захват в склянку **живого** существа; Грибошмыг: `spore_pouch` за кормление; Гулокрыл — приручаемый питомец, **не дроп как предмет**. Реальные рецепты/мирное получение, антидублирование, Creative Tab и RU/EN. `lost_halls_waymark` — ставится на стену/пол, светится, не перекрывает проход; `lost_halls_tuning_fork` — настоящий серверный поиск ближайшего записанного **существующего и доступного** зала/выхода в 48 блоках, с явным отсутствием цели, без загрузки чужих чанков. Действующий `LostHallsRooms.findNearest` — только backend, не готовый Камертон. Убедиться, что обычный игрок может добыть и скрафтить инструменты без OP.

### F. #293 — Постень, 650 HP и настоящая арена

Один серверный encounter на уникальную арену, одна общая bossbar. В фазе I 650→260 HP, ровно однократный split в **4 живые копии ×65 HP** (Скорбь/Гнев/Тление/Безмолвие), общий phase-II HP — сумма их текущего HP. Четыре различные читаемые атаки, rotation masks, телеграфы/LOS и safe wall transit между минимум двумя проверенными anchors; копии не выделяют отдельные soul/XP/loot. Подключить `PostenEncounters` к реальным entity events, hit handling, spawn/despawn/reload/reconciliation; не допустить повторной четвёрки и повторного босса после победы. После смерти последней копии **ровно один** гарантированный комплект: `posten_heart`, уже существующая `slavicmyths:soul`, руна и голова, каждый ×1. Зафиксировать crash/restart delivery policy прежде, чем считать at-most-once authorization доказанной фактической выдачей.

### G. #303 и #302 — руна и трофеи

Руна Теневого лика: **80 тиков невидимости**, ручной выход, **три** боевых приманки на **120 тиков**, исчезают с одного удара, ограниченное реальное воздействие/AI-aggro/cooldown; без дюпа, серверные ограничения и NBT/relog/MP. Сверить существующий `RuneFoundation` и предметы, не создавать дубли.

**Три** уникальные реально размещаемые 3D головы Сторожа чащи, Жареницы и Постеня, гарантированно ×1 за boss victory, без двойной награды в loot-table и event. Переиспользовать `TrophyHeads`/существующее `slavicmyths:zharenitsa_head`; floor/wall placement, drops и RU/EN. Голова Постеня плавно вращает четыре физические маски в пределах **≤6 блоков** игрока, останавливает цикл при **≥8**; только косметика на клиенте без серверного глобального сканирования.

### H. #294 — только финальная естественная интеграция

Новый biome registry в **существующем** `minecraft:the_nether`, без потери **5 vanilla** биомов, Навьей рощи и Чёрной гари, крепостей, бастионов, разрушенных порталов и старых миров. `NetherParametersMixin` сейчас различает **только** cinder/non-cinder: третью climate branch нужно добавить явно с проверкой поведения, иначе профиль окажется Навьей рощи. Все S1–S6, 5 natural spawn типов, 4 шептуновых варианта, рецепты/навигация и настоящий Постень доступны без `/summon`/OP. **В каждой полной связной области** есть детерминированно гарантированная доступная арена (не RNG независимого отсутствия), формальный критерий полной области фиксируется **перед** измерениями. Никаких FULL chunk loads/дальних синхронных поисков, бесконечных tick scans, конфликтов порядка генерации или телепорта в лаву.

## 4. Browser/GitHub workflow: как продолжать реализацию со мной

- Перед **каждой** порцией кода заново прочитать live `hell` HEAD/конкретные файлы/Issue, сверить, что нет нового конфликтующего коммита. Один writer для пересекающихся частей. `main`, `master`, `release`, старые PR не трогать без отдельного решения.
- Делать маленькие целевые изменения, одно функциональное направление за раз; не добавлять генераторы 1000 «заглушек». В браузерном сеансе изменять/создавать файлы непосредственно в `hell` через GitHub, сразу указывать полученный commit SHA и список фактических файлов. Не утверждать локальные тесты, которых не выполняли; GitHub edit ≠ Java compile.
- Первые независимые задачи **без PNG**: проверки и тесты опубликованных `SavedData` API (NBT/read-only), design + tests для server hooks, протокол idempotent room publication, lifecycle reconciliation Постеня, серверный item navigation contract, collision/registry inventory. Интеграционные классы не объявлять рабочими до появления consumer и валидных ресурсов.
- Когда оригиналы станут доступны в сессии/репозитории, пройти SOURCE_GATE и сразу продолжить A→H. Не подменять оригиналы сведениями о том, что ZIP существует в библиотеке. Художественные части остаются BLOCKED, но не тормозят самостоятельную логику.
- После серии GitHub-правок обновлять `REPORT.md` фактической матрицей. Для локальной сборки нужен Java21/NeoForge 1.21.1, `clean build`, offline logic tests и resource audit. Тестовые tools не включать в JAR. Пока runtime не разрешён и не запускался — `NOT_RUN_ENV_BLOCK`, `POLYMC_NOT_INSTALLED`.
- Не закрывать Issues, не ставить `Готово`, не объявлять выпуск без ручной проверки владельца. Не запускать Minecraft/сервер/GameTest/PolyMC без отдельного прямого разрешения.
