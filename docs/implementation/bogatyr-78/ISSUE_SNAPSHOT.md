# ИНДИВИДУАЛЬНОЕ ТЗ v4 • 20.10.2026

## УТВЕРЖДЕНО ВЛАДЕЛЬЦЕМ • 20.10.2026 — дополнение к #78

**Это одна задача #78; выполнять только после отдельного поручения.** Никаких попутных работ по другим issue. Все пункты исходного ТЗ ниже сохраняются, если не противоречат утверждённым уточнениям.

### А. Жёсткие ограничения жизненного цикла (утверждены)
- **Максимум 10 минут активного серверного игрового времени на один призыв каждого богатыря** (ориентир 12 000 тиков при 20 TPS). **Отступление, лечение и восстановление входят в эти же 10 минут**, не продлевают таймер и не начинают новый срок. Не увеличивать до 20 минут.
- **Не более 2 полноценных восстановлений/возвращений после поражения на один призыв**. Обычное лечение/питьё зелья до поражения не расходует эту квоту. **Третье поражение — окончательный выход из помощи**, без очередного бесконечного цикла `recovering → fresh → recovering`.
- **Отдельный cooldown 30 минут на КАЖДОГО из четырёх богатырей** после ухода по лимиту, гибели, исчерпания восстановлений или ручного отзыва. Вызов другого доступного богатыря не блокируется этим индивидуальным CD; исходный лимит группы 2 / 3 при событии Полоза сохраняется. Провалившаяся попытка вызова не запускает CD.
- КД и остаток времени/бюджета восстановлений устойчивы к relog/logout, перезапуску сервера, unload, смене мира; повторный вызов, отзыв и сериализация не сбрасывают лимит. Не создавать конкурирующий SavedData без необходимости.
- **Обязательные сюжетные схватки:** не убирать героя посреди необходимой фазы; таймер помощи допускает приостановку на обязательной фазе (без бесплатных новых восстановлений), корректно продолжить/завершить после неё. Сохранять действующие сюжетные права и ограничения, в том числе в боях с Калином/Картаусом/личными соперниками.

### Б. Появление (утверждено)
- **Обычный безопасный спавн рядом с игроком**, без растягивания, изменения масштаба, эффекта материализации из пустоты и насильственного перемещения/искажения модели. Не нужно заставлять богатыря обязательно бежать издалека.
- Проверить существующие `skim/HeroCalls.java`, `HeroArrivingUntil`, `ARRIVE`, клиентские render/model трансформации и частицы; исправлять **причину** растягивания, не маскировать поверх новой анимацией. Без телепорта в стену/лаву/незагруженный чанк; без изменений чужих моделей.

### В. Обязательный адресный QA звуков четырёх богатырей (новый дефект)
- **Жалоба владельца:** у **Алёши или Финиста** слышен неуместный «футуристический» звук; некоторые звуки богатырей воспринимаются поломанными. **Нельзя угадывать проблемный OGG по одному названию** — установить персонажа, событие (вызов, движение, атака, способность, ранение, восстановление, отзыв), фактически проигрываемый `SoundEvent` и исходный файл.
- Для **Ильи, Добрыни, Алёши, Финиста** сделать проверяемую таблицу `entity / действие / Java-вызов / event ID / sounds.json / фактический OGG / проверка в игре / вердикт`. Проверить регистрацию, корректность путей в JAR, звуковую привязку к кадрам, громкость, pitch, повторы/спам, варианты звука и отсутствие чужих/современных/синтетических сигналов там, где они неуместны. Найти неиспользуемые или неправильно подключённые варианты. Существующие хорошие звуки не заменять.
- **Приоритетные реальные точки проверки:** `alyosha.summon`, `entity.finist.summon_chime` и cues боевых/птичьих/магических действий — **только кандидаты на проверку, НЕ установленная причина**. Проверить также шаги/ранения/удары/голос у каждого богатыря.
- Исправлять только **подтверждённый дефект** неправильного подключения/проигрывания или неподходящего конкретного звука, сохраняя узнаваемое славянское/сказочное звучание. Не делать общий аудиоремастер, не менять других существ, не выдумывать новые аудиопакеты вместо проверки текущих.
- Сдача: перечень конкретных дефектных ID → что было слышно/что реально проигрывалось → исправленная связь/ресурс → проверка в клиенте. Если Minecraft не запускался или записи не прослушаны — помечать **`OWNER_PENDING`**, не утверждать, что звук исправлен или принят.

### Г. Обязательные регрессионные сценарии
0/1/2/3 поражения; ровно 10 минут с учётом времени восстановления; независимые КД Ильи/Добрыни/Алёши/Финиста; попытка раннего призыва; отказ из-за безопасного места; ручной отзыв; смерть; два игрока; reload и смена мира; обязательная сюжетная фаза; два/три допустимых героя; спавн в открытом мире и тесном пространстве; реальные звуки и анимации вызова, боя, лечения, отзыва.

## Подтверждённый дефект
Богатырь может бесконечно оставаться в мире после нескольких восстановлений, хотя сюжетно он временный помощник. Нужен конечный lifecycle, **без исчезновения во время обязательной фазы боя**.

## Схема состояний
**[State diagram #78](https://github.com/Deserag/slavic-myths/blob/main/docs/design/MECHANICS_FLOW_BLUEPRINTS.svg)**. `READY → SUMMONED → HELPING → RECOVERING (с лимитом) → RETURNED → COOLDOWN → READY`; ответвления: смерть, бесхозность, logout/unload, другой мир, отмена миссии, пауза во время mandatory encounter.

**Имеющийся код:** `BogatyrLedger`, `HeroCalls`, `IlyaEntity`, `DobrynyaEntity`, `AlyoshaEntity`, `FinistEntity`, `KalinParty`, соответствующие SavedData и companion HUD. Не строить второй SavedData для времени, если его уже содержит служба вызова.

## Исполнение
1. Для каждого из четырёх существ отметить нынешнее правило сохранения/отзыва/регенерации в коде; отдельные сюжетные исключения сохранять. Отдельно устранить конкретный путь `recovering → fresh → recovering` без конечной границы.
2. Задать **единую модель** ограничений `summonTime`, `expiry`, `recoveryCount`, `readyAt` по server gameTime/устойчивым SavedData; использовать утверждённые владельцем численные ограничения из раздела «УТВЕРЖДЕНО» выше; другие значения не придумывать.
3. Когда лимит истёк — управляемый recall/despawn с удалением карты owner↔entity и корректным восстановлением вызова после CD, никакого лута/триггера убийства и дублирования героев.
4. Сообщение игроку: `ещё доступен / осталось время / восстанавливается / возвращается / следующий вызов через …`; данные для HUD #90 синхронизируются сервером, но большой UI-рефакторинг **не в #78**.

## Подтверждённое существующее ограничение состава (важно)

В `skim/HeroCalls.java` фактический лимит группы: **2 героя обычно и 3 во время события Полоза** (`count(p)>=(polozParty?3:2)`). Таймеры и восстановления нельзя реализовывать так, чтобы случайно изменить этот лимит. #90 отвечает только за корректный HUD третьего законного героя, а не за создание права на четвёртого.

## Не повредить
Квестовые summon-права, однопользовательский/MP, поддержку боёв Калина/Картауса и другие обязательные испытания, блокировку вызова в активной схватке. Не сбрасывать состояние cooldown при перезаходе/переключении мира.

## Контрольные случаи
Первый вызов; 1/2/лимит восстановлений; таймер в мире; disconnect+relogin; сохранение/перезапуск; 2 игрока одновременно; смерть/withdraw; герой в сюжетной обязательной арене. До/после на логах lifecycle, а не только «теперь исчезает».

## Правило приёмки и безопасности

- **Сначала подтвердить source HEAD и исходный вид**, затем сделать **минимальную необходимую правку**, затем сравнить с тем же ракурсом/масштабом/состоянием и проверить **регрессии соседних функций**. Наличие кода, успешно собранный JAR и концепт НЕ означают корректный вид/игровую работу.
- Не менять registry ID, NBT/world saves, баланс, модель другого персонажа, механизмы иных веток, если этого не требует дефект. Не делать массовой перерисовки или общего рефакторинга «заодно»; актуальный рабочий main не восстанавливать и не откатывать.
- Один исполнительный пакет в рамках issue; никаких сообщений владельцу каждые 5 минут. Итог одним сообщением: HEAD/commit, точный список изменённых файлов, **сравнение по обязательным видам/сценариям**, Java21 build + resource/JAR checks, ручная игровая проверка — `OWNER_PENDING` до решения владельца. После 2–3 законченных пакетов — короткий handoff в новый чат Codex, без повторного аудита.
