## Участники и полномочия

- **Владелец проекта**: утверждает идеи, рамки/ТЗ, приоритеты и релиз; проводит игровую приёмку; единственный переводит задачу в «Готово», подтверждает отмену и разрешает закрытие Issue.
- **ChatGPT (обсуждение и планирование)**: систематизирует идеи, анализирует GitHub и реальные исходники, предлагает формулировки и зависимости, готовит ТЗ/подзадачи, фиксирует согласованные решения. Не выдаёт план за реализованный код и не меняет приоритет без решения владельца.
- **Codex (исполнение)**: берёт *явно порученную* задачу из очереди; реализует только согласованный scope, публикует проверяемые результаты, обновляет статус «В работе»/«Тестирование» при наличии доступа к Project и основания. Не принимает работу от лица владельца и не закрывает Issue.
- **GitHub Project**: единая доска состояния (не второе хранилище ТЗ); один элемент — одна Issue либо черновая идея. Статус Project не равен Issue state open/closed.

### Переходы

Нормальная цепочка: **Концепция → Анализ → Ожидание → В работе → Тестирование → Готово**.

- **Тестирование → Доработка → В работе → Тестирование**, пока владелец не примет результат.
- **В работе / Доработка / Тестирование → Анализ**, если обнаружен неверный замысел, недостающий референс, конфликт архитектуры или пересмотренный scope; старая работа сохраняется в истории.
- **Анализ → Концепция**, если идея снова отложена и не готова к спецификации.
- **Ожидание → Анализ**, если ТЗ утратило актуальность или появился вопрос, без которого нельзя исполнять.
- **Любой незавершённый этап → Отменена** только по решению владельца.
- **Готово → Доработка/Анализ** только по прямому решению владельца при регрессии или пересмотре; предпочтительна новая отдельная Issue на новый дефект, чтобы сохранить историю приёмки.
- Обозначение «отложено» — **отдельный признак**, а не девятый статус: готовая, но отложенная задача остаётся в «Ожидании», незрелая идея — в «Концепции».

### Как определяется переход в «Тестирование»

Codex может передать работу в тестирование, когда:
1. Все пункты **исполнительского scope** закрыты действительным результатом, а не концептом, чертежом или черновым PR.
2. Есть точные source/commit, изменённые registry ID и файлы, сравнения до/после для графики и моделей, проверка совместимости миров.
3. Выполнены применимые Java 21 clean build, resource/JAR проверки, необходимые автоматические QA и регрессионные проверки; нет незакрытых **исполнительских** FAIL/BLOCKED/NOT_RUN.
4. Есть итоговая матрица **REQUIREMENT | EVIDENCE | PASS / FAIL / BLOCKED / NOT_RUN** и явный список сценариев для теста владельца.
5. Если запуск Minecraft/PolyMC запрещён Codex, игровые проверки честно остаются OWNER_PENDING/NOT_RUN: это **ожидаемый предмет этапа «Тестирование»**, а не утверждение о пройденном runtime. Если фактически не собран JAR или не готов обязательный asset, задача остаётся «В работе».
6. Готовое к проверке содержимое действительно доступно владельцу. Для утверждения «установлено» необходимы installed path/version/SHA256 и проверка отсутствия двух JAR; иначе указывать POLYMC_NOT_INSTALLED. Нельзя путать «собрано» с «установлено».

До явной приёмки владельцем никакие слова DONE/ACCEPTED/owner-accepted, закрытие Issue, автоматическое завершение родителя недопустимы. Эти требования дополняют, а не заменяют [AGENTS.md](../AGENTS.md).

## Как вести Issue

1. **Концепция**: короткое название идеи, «зачем», что неизвестно, почему откладываем; желательно Draft issue внутри Project. Не поручать код.
2. **Анализ**: проверить текущую реализацию, сохранить наблюдения владельца, решить scope/non-goals, реальные ID/файлы, требования, зависимости и приёмочные сценарии. Не создавать массовую работу «про запас».
3. **Ожидание**: одна утверждённая Issue или родитель + все необходимые дочерние задачи, связанные чек-листом и ссылками **независимо от номеров**. Подзадача #150 не пропускается из-за того, что Codex сейчас исполняет #87.
4. **В работе**: один writer для main/общих генераторов, явное поручение, журнал изменения. Другие задачи не начинать автоматически после коммита.
5. **Тестирование**: версия тестовой сборки, ссылка на отчёт, точный список игровых проверок. Владелец отмечает PASS/FAIL; при FAIL фиксирует замечание и переводит в «Доработка».
6. **Готово / Отменена**: оставить причину и дату решения. Completed требует личной приёмки, not_planned — явной отмены (не ложной приёмки).

Если Issue содержит дочерние задачи, **родитель — трекер**, а не разрешение выполнить всё одним коммитом. Родитель нельзя считать «Тестирование», пока исполнительские части дочерних задач не представлены к проверке; «Готово» — пока не приняты все обязательные дети. Исторические closed-issue со статусом «спецификация готова, production не начат» не переводить в «Готово» по одному признаку GitHub Closed.

## Контроль ежедневной работы

Для статуса проекта использовать GitHub Project. Для проверки «что реально сделано» читать **Issue + комментарии + отчёты в docs/implementation + соответствующий source/commit + фактическую игровую приёмку**. Подготовленное ТЗ, нарисованный SVG, PASS сборки, закрытый не по приёмке Issue или текст «Done» в PR не доказывают игровую готовность.
